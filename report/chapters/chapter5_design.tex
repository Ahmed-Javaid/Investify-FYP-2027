\chapter{Software Design Specification}

\section{Design Scope and Rationale}
This design specification describes the implemented Mid-1 record, evidence, profile and explanation-checking module. The handbook permits the design models appropriate to the project; the selected component, domain, layered, data-flow, sequence, activity, state and deployment models answer different implementation questions. A relational database is not implemented: the schema diagram describes the actual JSON/Parquet artifact contracts and digest relationships. No screen or diagram implies a trained student, a production service or supervisor approval.

The key decision is to keep recorded classifier facts authoritative. A profile changes a separate retrospective comparator, and an explanation cannot overwrite model probabilities. The input validator checks probabilities, class argmax, feature/attribution consistency and missing values before a view appears. The verifier checks displayed text and structured claims independently; the emission path retains a rejected candidate while checking its replacement.

An equity study has dated market observations, derived feature evidence and a model run. A recorded decision case connects probabilities and attributions to a particular session/source. Explanation checking consumes that case. The prototype profile is an independent comparison, as the concrete class model below shows; no investor account or personalized classifier is invented.

\section{Component and Layer Design}
\begin{figure}[htbp]\centering\input{figures/mid1_components}\caption[Implemented components and interfaces]{Implemented component dependencies. The presentation controller calls the recorded-data adapter, verification pipeline and independent profile comparator.}\label{fig:components}\end{figure}
The main entry point is \nolinkurl{app/streamlit_app.py}. \nolinkurl{app/presenter.py} renders only the selected workspace and walkthrough step. \nolinkurl{app/presenter_data.py} reads a fixed source registry, validates every recorded decision and refuses duplicate sessions, inconsistent model collections or changed bytes. A collection identity includes the full artifact hash; this prevents a check for one source revision from appearing as a check for another.

\begin{figure}[htbp]\centering\input{figures/mid1_layers}\caption[Layer responsibilities]{Responsibilities from presentation through application and domain contracts to recorded artifacts. Offline scientific execution is separate from page rendering.}\end{figure}
Streamlit provides the current presentation interface; the original standard-library HTTP demonstration remains an alternate historical interface. Neither opening the UI nor reading a study runs model training. Scientific execution uses its separately prepared runtime and original verified publisher weights, while the current interface reads completed results.

\section{Domain Model}
\begin{figure}[htbp]\centering\input{figures/mid1_domain}\caption[Live-module class/domain model]{Implemented domain objects and their principal associations. A case collection owns session-indexed records; each record contains ranked feature contributions. Research-study evidence remains separate from the live classifier.}\label{fig:domain}\end{figure}
\texttt{DecisionRecord} is the factual boundary. Its dataclass rejects impossible probability or attribution states; nested dictionaries remain ordinary mappings and downstream functions treat them as read-only. \texttt{Explanation} contains visible text and an optional claim payload. \texttt{VerificationResult} retains per-claim verdicts and four metrics. \texttt{EmittedExplanation} carries accepted or verified fallback output plus the rejected candidate/report when present. A \texttt{RiskProfile} contains capacity, tolerance, caps and the reconciled score; its result is a separate comparison rather than a new prediction.

\section{Data Flow and Artifact Schema}
\begin{figure}[htbp]\centering\input{figures/mid1_dataflow}\caption[Live-module logical data flow]{Logical data flow for a selected case. The current text and JSON meet at the verifier; profile answers flow to a separate comparator.}\label{fig:dataflow}\end{figure}
The reviewer supplies a source/session choice, optional profile answers and a candidate explanation. Validation reads the recorded data store, context supplies maintained meanings, verification checks the selected record, and the comparator uses earlier scaling rows. These paths return visible evidence, checked prose and comparison outputs. Social/teacher data is read only in its own research workspace.

\begin{figure}[htbp]\centering\input{figures/mid1_schema}\caption[Artifact schema and digest relationships]{Actual artifact relationships expressed through source, plan, model and run digests. This is a file-schema design, not a claim of an implemented SQL database.}\label{fig:schema}\end{figure}
A scientific run binds input, configuration, source and runtime identities. Its model, scaler and calibration traces and decision records are retained under a new run directory. The social benchmark binds a frozen plan; each candidate bundle binds that plan, model revision, raw logits and execution receipts. Teacher packets bind record facts and split identities; accepted prose is exported to training/validation with held-out test dates excluded.

\section{Behavior and Sequence Design}
\begin{figure}[htbp]\centering\input{figures/mid1_sequence}\caption[Explanation-check system sequence]{System sequence for the live explanation check, including the retained rejection and independently checked fallback.}\label{fig:ssd}\end{figure}
The controller receives the current candidate, not an earlier cached result. \nolinkurl{explain/pipeline.py:emit} invokes \nolinkurl{explain/verifier.py:verify}. A passing candidate is emitted; a failure keeps its report, renders the deterministic template and verifies it independently. If the template check itself fails, the operation raises an error and the UI claims no verified output.

\begin{figure}[htbp]\centering\input{figures/mid1_activity}\caption[Accepted and fallback activity flow]{Activity flow and the two visible success paths. The failure path does not silently accept the candidate.}\end{figure}
\begin{figure}[htbp]\centering\input{figures/mid1_state}\caption[Explanation-view state transitions]{Explanation-view state machine. A case or text edit invalidates the visible check; only a result for the current identity can appear as accepted.}\end{figure}
The candidate cache identity combines source, session, artifact digest and text digest. Changing cases resets the candidate to that record's template; editing text hides a previous verdict until checking runs again. Independent profile state can persist between steps without altering classifier facts.

\section{Interface and Failure Contracts}
\begin{longtable}{p{0.26\textwidth}p{0.34\textwidth}p{0.30\textwidth}}\toprule Operation & Result & Failure behavior\\\midrule
Select recorded case & Validated record/context & Missing, duplicate, inconsistent or changed input shows an error; no substituted case.\\
Check explanation & Candidate/report or verified fallback & Known contradiction, malformed claims, missing essential claims and strict unsupported prose reject.\\
Apply profile & Reconciled profile and separate blend & Incomplete answers produce no score; development sessions refuse comparison.\\
Read study & Recomputed receipt-bound metrics & Invalid/partial evidence withholds comparison; no neutral substitute for failures.\\
Optional local generation & Explicit model request and checked output & Unconfigured model gives labelled deterministic guide; retry/timeout/identity limits remain explicit.\\
\bottomrule\end{longtable}
The portable historical API additionally exposes catalogue, record, verification, guide and profile/comparator endpoints. It rejects unknown routes, malformed/nonfinite JSON and oversized bodies. Those contracts and their live HTTP checks remain in the dated source handover; they do not establish browser visual quality or production security.

\section{Deployment and Security Design}
\begin{figure}[htbp]\centering\input{figures/mid1_deployment}\caption[Local deployment topology]{Current local topology. The viewer binds loopback; publisher weights and temporary builds stay on E:. Scientific execution and optional generation are distinct operations.}\end{figure}
The launch script binds \nolinkurl{127.0.0.1:8507}, disables usage telemetry and keeps cache/scratch on E:. It refuses an occupied port. The UI has no broker/account access, authentication or transaction path. Profiles stay in session memory; no profile database is implemented. Credentials stay in ignored local configuration and are excluded from review archives. This is a local review topology; a production target and authentication/deployment threat model remain later work.

\section{Alternatives and Design Evolution}
\begin{longtable}{p{0.22\textwidth}p{0.32\textwidth}p{0.36\textwidth}}\toprule Decision & Alternative considered & Rationale and remaining limitation\\\midrule
One active workspace & All tabs mounted at once & Reduces competing controls and unnecessary hidden work; preserves explicit movement through the core demonstration.\\
Independent prose/JSON checks & Trust structured claims alone & A wrong displayed probability can coexist with correct JSON; the regression and live failure demonstrate the corrected boundary.\\
Deterministic fallback & Emit a failed candidate & Keeps supported record facts visible and retains the failure report; arbitrary language understanding is unproven.\\
Separate profile comparator & Relabel saved model output & Demonstrates prototype weighting without falsely claiming personalized XGBoost or suitable investor actions.\\
Artifact storage & Introduce SQL persistence & Actual interfaces consume immutable study files and transient profiles; adding a database would imply unsupported implementation.\\
Recorded studies in separate workspace & Train during presentation & Preserves reproducible source identities and a short core demonstration; live generation/training is not inferred.\\
\bottomrule\end{longtable}
The previous UI exposed four densely populated research tabs, then a guided wrapper. User review identified clutter; the present revision isolates the four-step case walkthrough and moves study details to their own workspace. This is an authorized presentation/design change. Scientific inputs, labels, model identities, thresholds and historical evidence remain unchanged.
